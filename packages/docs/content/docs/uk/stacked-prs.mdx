# Стеки pull request-ів

Стек (stack) це ланцюжок pull request-ів, де кожен спирається на той, що під ним: базова гілка другого PR це гілка першого, і так далі. Такий поділ великої зміни залишає кожен PR достатньо малим для рев'ю. OpenChamber показує весь стек усюди, де з'являється його PR, і допомагає тримати ланцюжок у порядку.

Стеки працюють із GitHub. Якщо GitHub сам знає стек (його власні стекові pull request-и), OpenChamber читає стек GitHub. Інакше він знаходить ланцюжок за базовими гілками PR, що охоплює й форки та GitHub Enterprise Server.

## Перегляд стеку

Відкрийте pull request зі стеку на дошці [Завдання та PR](/uk/issues-and-prs/), у вигляді pull request або у вигляді **Git**. У його попередньому перегляді є розділ **Pull request stack**, що перелічує всі PR знизу вгору. Кожен рядок показує стан PR, його перевірки та чи є конфлікти, і позначає той, який ви дивитеся. Рядок, який не вдалося прочитати, каже про це замість кольору.

У списку дошки PR зі стеку має маленький значок із місцем у стеку, наприклад **2/3**. Клацніть рядок у стеку, щоб відкрити цей PR.

Рядок також може попереджати:

- **Behind base by N commits**: PR під ним змінився, тож цьому потрібен restack.
- **Base was merged. Retarget to main.**: PR під ним злито, а цей досі вказує на його стару гілку.
- **Still carries the commits of merged #N**: PR під ним злито в trunk через squash, а цей досі містить його старі коміти.

## Відкрити PR поверх іншого

1. Зробіть checkout гілки для нового PR, взявши за початок гілку верхнього PR.
2. У розділі стеку натисніть **Open stacked PR on top** або виберіть гілку верхнього PR як базу у формі створення у вигляді **Git**.
3. Форма покаже **Stacked on #N**. Напишіть заголовок і опис та створіть PR.

На GitHub.com OpenChamber також реєструє новий PR у власному стеку GitHub. Якщо GitHub відмовляє (форк, старіший сервер), PR усе одно створюється, а стек і далі показується.

## Restack після зміни нижче

Коли PR низько в стеку отримує нові коміти, PR над ним застарівають. Натисніть **Fetch and restack**. OpenChamber робить fetch віддаленого репозиторію, по черзі ребейзить кожну гілку на ту, що під нею, а потім пушить гілки, які зсунулися. Push відхиляється, якщо тим часом хтось інший запушив у гілку, тож нічия робота не перезаписується.

Зсуваються лише власні коміти кожної гілки. Після squash-злиття нижче старі коміти злитого PR залишаються поза.

### Коли restack натрапляє на конфлікт

Restack зупиняється на PR, що має конфлікт. Гілки під ним лишаються з виконаним restack, гілки над ним чекають. Що далі, залежить від **Settings → Integrations → GitHub → Restack conflicts**:

- **Pause and let me choose** (типово): розв'яжіть конфлікт у теці, яку називає розділ стеку, додайте файли в stage і натисніть **Continue**. **Abort** повертає цю гілку, де вона була, і пропускає решту. **Ask the session to resolve** передає конфлікт сесії, у якій ви перебуваєте.
- **Let the session resolve it**: конфлікт одразу йде до сесії. Коли її хід завершується без нерозв'язаного, restack продовжується сам.

## Злиття стеку

Зливайте знизу вгору. Розділ стеку пропонує **Merge bottom PR #N** лише для найнижчого відкритого PR, вашим звичним способом злиття. Після злиття наступний PR переходить на trunk, а **Fetch and restack** прибирає з нього злиті коміти. Тоді зливайте наступний.

## Робота над усім стеком у сесії

- **Attach whole stack** у розділі стеку додає до поля повідомлення diff, перевірки й коментарі кожного PR разом із підсумком порядку та гілок. Якщо один PR не вдалося прочитати, решта все одно додаються, і вам скажуть, який не вдався.
- У списку **Linked** сесії увімкніть **Follow whole stack** для прив'язаного PR. Відтоді сесія стежить за стеком, коли він змінюється: нові PR зверху, злиття та зміни цілі з'являються без повторної прив'язки.

## Де це працює

Стеки працюють у вебзастосунку, застосунку для комп'ютера та мобільних застосунках. Розширення VS Code стеки не показує.
