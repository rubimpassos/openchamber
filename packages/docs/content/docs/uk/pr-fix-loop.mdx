# Цикл виправлення PR

Цикл виправлення тримає сесію за роботою над одним pull request, доки він не буде готовий до злиття. OpenChamber стежить за перевірками та рев'ю PR. Коли CI падає, сесія отримує невдалі перевірки з їхніми кроками, анотаціями й рядками логів. Коли хтось робить рев'ю чи коментує, сесія отримує цей відгук, вносить зміну й відповідає в PR. Цикл працює на вашому сервері OpenChamber, тож триває й при закритому застосунку.

Він завершується, коли PR готовий: CI зелений, жодна гілка обговорення рев'ю не лишилася нерозв'язаною, і ніхто не чекає на запрошені зміни. Тоді ви отримуєте сповіщення, а також коли цикл зупиняється з іншої причини.

## Запуск циклу

1. Відкрийте сесію, яка має виконати роботу.
2. Знайдіть pull request на дошці [Завдання та PR](/uk/issues-and-prs/), у вигляді pull request або у списку **Linked** сесії та виберіть **Start fix loop**.
3. Перевірте налаштування в діалозі й натисніть **Start fix loop**.

Цикл показано вгорі поля повідомлення сесії: PR, що робить цикл, кількість ітерацій і стан CI. Звідти можна змінити його налаштування, відкрити PR на дошці або зупинити його кнопкою **Stop**.

## Що отримує сесія

- **Після push** цикл чекає на CI для нового коміту. Якщо він падає, сесія отримує невдалі перевірки раз на коміт, ніколи двічі ту саму помилку.
- **Для кожного рев'ю, коментаря до рев'ю чи нового коментаря**, що враховується за вашими налаштуваннями, сесія отримує його текст і посилання. Її просять відповісти в PR та закрити гілки обговорення, які вона виправила. Щоб відповідати й закривати гілки обговорення, сесії потрібні власні автентифіковані інструменти GitHub. Обліковий запис циклу використовується лише для читання PR.

Якщо сесія зайнята, повідомлення чекає в її черзі й іде, коли хід завершується. Якщо до GitHub не достукатися, цикл зберігає те, що знав, і каже, що не зміг перевірити. Невдалу перевірку він ніколи не читає як зелену.

## Налаштування

Типові значення містяться в **Settings → Integrations → GitHub → Fix loop**, і кожен цикл може їх змінити.

- **Maximum iterations**: скільки разів цикл може надсилати роботу сесії (типово 10).
- **Token budget**: зупиняє, щойно сесія витратила стільки токенів від початку циклу. Порожнє значення означає відсутність бюджету. Бюджет перевіряється після кожного ходу, тож один хід може його перевищити.
- **Respond to**: **CI and reviews**, **CI only** або **Reviews only**.
- **Ignore my feedback**: пропускає коментарі з облікового запису GitHub, яким цикл читає PR. В автоматичному режимі сесія відповідає зі своїм власним обліковим записом GitHub, і якщо він відрізняється від облікового запису для читання, ви додаєте його до **Blocked authors**. У режимі із підтвердженням відповідає сервер з облікового запису GitHub, прив'язаного до циклу, а воркер не має облікового запису GitHub.
- **Ignore bots**: пропускає коментарі ботів.
- **Allowed authors** і **Blocked authors**: логіни GitHub через кому. Якщо є список дозволених, враховуються лише ці люди.
- **Only comments that mention this text**: враховує коментар лише тоді, коли він містить текст згадки (типово `@openchamber`).
- **Push changes**: **Push automatically** або **Wait for my approval**. Автоматичний режим зберігає власний робочий процес сесії з GitHub. Режим із підтвердженням виконує виправлення в обмеженому воркері й потребує окремого налаштування.

## Режим із підтвердженням

З **Wait for my approval** сесія не робить push. Обмежений воркер виправляє PR в ізольованому просторі, і жодна зміна не публікується на GitHub, доки ви не підтвердите точний коміт. Сервер і далі читає PR з GitHub, поки цикл працює.

### Налаштування воркера

1. Увімкніть ізольовані простори й налаштуйте для них місце. Цикл виправлення ніколи не вмикає це за вас.
2. У вікні запуску знайдіть **Restricted worker**. Виберіть, де працює воркер, і його модель, а тоді натисніть **Prepare new worker**. Це створює новий простір, який використовує лише цей воркер. Наявний простір не можна повторно використати чи перетворити.
3. Надайте моделі воркера доступ у вікні доступу. Доступ отримує лише вибрана модель. Токени моделі тримає gatekeeper, воркер їх не бачить. Використання моделі йде з вашої квоти.
4. Head-репозиторій PR, зокрема форк, потребує керованого пункту призначення для push Git саме для цього репозиторію. Якщо його немає, вікно відсилає до налаштувань Git.
5. Коли вікно покаже, що воркер готовий, натисніть **Start fix loop**.

Воркер не має доступу до GitHub чи будь-якої іншої мережі, лише до моделі. Запасного переходу на системний чи фоновий push немає. Цикл не стартує, якщо воркер не готовий або бракує доступу. Модель чи власну кінцеву точку, які не перевірено для обмежених воркерів, відхиляють, і її ніколи не підміняють іншою.

**Forget worker selection** прибирає лише вибір. Простір і його файли лишаються, ними керують в ізольованих просторах.

### Перегляд і публікація

Коли хід завершується, сервер експортує коміт воркера й зберігає його як квитанцію з точним репозиторієм, гілкою та очікуваним віддаленим head. Тоді цикл показує **Review publication**. Відкрийте **Inspect exact changes**, перевірте їх і натисніть **Approve and publish commit**. Звичайна кнопка push Git не підтверджує квитанцію. Публікацію відхиляють, якщо PR закрито або змінилися віддалений head, гілка чи репозиторій. Квитанція й робота лишаються для перегляду.

### Відповіді після публікації

У вікні перегляду є **Automatic GitHub replies**: згенеровані відповіді та треди, які буде розв'язано. Це текст воркера, тож прочитайте цитований текст перед підтвердженням. Після публікації коміту сервер публікує відповіді й розв'язує треди власним доступом на запис до GitHub, який не походить від воркера. Це відбувається і при закритих клієнтах. Якщо запис не вдався, цикл показує це й не повідомляє, що PR готовий.

### Зупинка, відновлення й бюджет

**Stop** зупиняє воркер і зберігає код та квитанцію. **Resume fix loop** знову перевіряє воркер і запускає його, і лише після цього можна опублікувати квитанцію зупиненого циклу. Забування завершеного циклу не видаляє його простір.

Режим виконання фіксований для кожного циклу. Завершіть очікувані публікації та відповіді на GitHub, перш ніж зупинити цикл і почати інший режим. Налаштування також заблоковані, доки очікує квитанція або відповіді на GitHub.

Бюджет токенів перевіряється після кожного ходу, тож хід може його перевищити. Коли бюджет досягнуто, нові ходи моделі не стартують, але очікуваний експорт, публікація й відповіді ще можуть завершитися. Потім цикл показує статус бюджету токенів.

### Де працює режим із підтвердженням

Сервер виконує цикл при закритих клієнтах. Вебзастосунок, застосунок для комп'ютера й мобільні застосунки ділять цей сервер. Розширення VS Code не пропонує режим із підтвердженням.

## Коли цикл зупиняється

| Статус | Причина |
| --- | --- |
| PR готовий | CI зелений, немає нерозв'язаних гілок, немає запрошених змін |
| PR закрито | PR злито або закрито |
| Ліміт ітерацій | Цикл надіслав роботу стільки разів, скільки дозволено |
| Бюджет токенів | Сесія вичерпала бюджет |
| Зупинено | Ви зупинили його або сесію видалено |

Зупинений цикл лишається вгорі поля повідомлення, доки ви його не закриєте. У режимі із підтвердженням, коли очікує квитанція або відповіді на GitHub, робота зберігається, а цикл лишається; скористайтеся **Resume fix loop**, щоб продовжити наявний цикл. Повторний запуск на тому самому PR починає новий цикл лише тоді, коли немає очікуваної публікації чи відповідей.

## Стеки

Кожен pull request має власний цикл. У [стеку](/uk/stacked-prs/) запустіть цикл на кожному PR, який хочете виправити; збій в одному PR не затримує інші.

## Де це працює

Цикл працює на сервері OpenChamber за вебзастосунком, застосунком для комп'ютера та мобільними застосунками. Розширення VS Code його не пропонує.
