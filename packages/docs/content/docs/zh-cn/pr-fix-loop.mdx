# PR 修复循环

修复循环让会话持续处理同一个拉取请求，直到它可以合并。OpenChamber 会盯着 PR 的检查和评审。CI 失败时，会话会收到失败的检查，以及它们的步骤、注释和日志行。有人评审或评论时，会话会收到这些反馈，做出修改，并在 PR 上回复。循环运行在你的 OpenChamber 服务器上，所以关闭应用后它也会继续。

PR 准备好时循环结束：CI 通过，没有未解决的评审讨论串，也没有人在等待被要求的修改。此时你会收到通知，循环因其他原因停止时同样会通知你。

## 启动循环

1. 打开要完成这项工作的会话。
2. 在 [Issue 与 PR](/zh-cn/issues-and-prs/) 看板、拉取请求视图或会话的 **Context sources**（PR 那一行的 **⋮** 菜单）中找到该拉取请求，选择 **Start fix loop**。
3. 检查对话框中的设置，然后点击 **Start fix loop**。

循环显示在会话消息框的顶部：PR、循环正在做什么、迭代次数和 CI 状态。在这里你可以修改它的设置、在看板中打开 PR，或点击 **Stop** 停止它。

## 会话会收到什么

- **push 之后**，循环等待新提交的 CI。如果失败，会话每个提交只会收到一次失败的检查，同一个失败不会收到两次。
- **对于按你的设置计入的每条评审、评审评论或新评论**，会话会收到其内容和链接。会话会被要求在 PR 上回复，并解决它已修复的讨论串。要回复并解决讨论串，会话需要自己已认证的 GitHub 工具。循环的账号只用于读取 PR。

如果会话正忙，消息会在它的队列中等待，并在这一轮结束后发出。如果无法连接 GitHub，循环会保留已知的状态，并说明它未能检查。它绝不会把失败的检查当成通过。

## 设置

默认值位于 **Settings → Integrations → GitHub → Fix loop**，每个循环都可以修改。

- **Maximum iterations**：循环最多可以向会话发送多少次工作（默认 10）。
- **Token budget**：自循环开始后，会话用掉这么多 token 时停止。留空表示没有预算。预算在每一轮结束后检查，所以单轮可能超出预算。
- **Respond to**：**CI and reviews**、**CI only** 或 **Reviews only**。
- **Ignore my feedback**：跳过循环读取 PR 所用 GitHub 账号的评论。自动模式下，会话用它自己的 GitHub 账号回复；如果与读取账号不同，请把它加入 **Blocked authors**。审批模式下，由服务器用绑定到该循环的 GitHub 账号回复，worker 没有 GitHub 账号。
- **Ignore bots**：跳过机器人的评论。
- **Allowed authors** 和 **Blocked authors**：GitHub 用户名，用逗号分隔。设置了允许列表时，只计入这些人。
- **Only comments that mention this text**：只有包含提及文本（默认 `@openchamber`）的评论才会计入。
- **Push changes**: **Push automatically** 或 **Wait for my approval**。自动模式沿用会话自己的 GitHub 工作流。审批模式在受限 worker 中执行修复，需要单独设置。

## 审批模式

选择 **Wait for my approval** 后，会话不会 push。受限 worker 在隔离空间中修复 PR，在你批准确切的提交之前，不会有任何更改发布到 GitHub。循环运行期间，服务器仍会从 GitHub 读取 PR。

### 设置 worker

1. 启用隔离空间，并为它配置运行位置。修复循环不会替你打开这个功能。
2. 在启动对话框中找到 **Restricted worker**。选择 worker 的运行位置和模型，然后点击 **Prepare new worker**。这会创建一个只供该 worker 使用的新空间。已有空间无法复用或转换。
3. 在访问对话框中为 worker 的模型授予访问权限。只授权你所选的模型。模型令牌由 gatekeeper 保管，worker 看不到。模型用量会计入你的额度。
4. PR 的 head 仓库（包括 fork）需要一个针对该确切仓库的受管 Git push 目标。缺少时，对话框会引导你到 Git 设置。
5. 对话框显示 worker 已就绪后，点击 **Start fix loop**。

worker 只能访问模型，无法访问 GitHub 或其他网络。没有回退到系统或环境 push 的路径。worker 未就绪或缺少访问权限时，循环不会启动。未针对受限 worker 审核的模型或自定义端点会被拒绝，不会被换成别的模型。

**Forget worker selection** 只移除这个选择。空间及其文件会保留，你可以在隔离空间中管理。

### 审查并发布

一个回合结束后，服务器会导出 worker 的提交，并把它连同确切的仓库、分支和预期的远程 head 保存为回执。循环随后显示 **Review publication**。打开 **Inspect exact changes** 检查内容，然后点击 **Approve and publish commit**。普通的 Git push 按钮不会批准回执。如果 PR 已关闭，或远程 head、分支、仓库发生了变化，发布会被拒绝，回执和工作成果会保留以供查看。

### 发布后的回复

审查对话框会列出 **Automatic GitHub replies**：生成的回复，以及将被解决的讨论串。这些是 worker 写的文字，批准前请先读引用的内容。提交发布后，服务器用自己的 GitHub 写入权限发布回复并解决讨论串，这个权限不来自 worker。所有客户端关闭时也会这样执行。如果某次写入失败，循环会显示出来，并且不会把 PR 报告为就绪。

### 停止、恢复与预算

**Stop** 会停止 worker，并保留代码和回执。**Resume fix loop** 会重新校验并重启 worker，已停止循环的回执只能在此之后发布。忘记一个已结束的循环不会删除它的空间。

执行模式在每个循环中固定。请先完成待处理的发布和 GitHub 回复，再停止循环并启动其他模式。回执或 GitHub 回复待处理时，设置也会被锁定。

token 预算在每个回合后检查，所以一个回合可能超出预算。达到预算后不会再开始新的模型回合，但待处理的导出、发布和回复仍可完成。之后循环会显示 token 预算状态。

### 审批模式的适用范围

服务器在所有客户端关闭时也会运行循环。Web 应用、桌面应用和移动应用共用这个服务器。VS Code 扩展不提供审批模式。

## 循环何时停止

| 状态 | 原因 |
| --- | --- |
| PR 已就绪 | CI 通过，没有未解决的讨论串，没有被要求的修改 |
| PR 已关闭 | PR 已合并或关闭 |
| 迭代上限 | 循环已按允许的次数发送了工作 |
| Token 预算 | 会话用完了预算 |
| 已停止 | 你停止了它，或会话被删除 |

已停止的循环会一直留在消息框顶部，直到你关闭它。审批模式下，如果回执或 GitHub 回复待处理，工作成果会保留，循环也会留着；用 **Resume fix loop** 继续现有循环。只有没有待处理的发布或回复时，才能在同一个 PR 上开始新的循环。

## 堆叠

每个拉取请求都有自己的循环。在[堆叠](/zh-cn/stacked-prs/)中，为每个想要修复的 PR 启动一个循环；某个 PR 的失败不会拖住其他 PR。

## 适用范围

循环运行在 Web 应用、桌面应用和移动应用背后的 OpenChamber 服务器上。VS Code 扩展不提供该功能。
