# PR fix loop

The fix loop keeps a session working on one pull request until it's ready to merge. OpenChamber watches the PR's checks and its review. When CI fails, the session gets the failed checks with their steps, annotations and log lines. When someone reviews or comments, the session gets that feedback, makes the change and replies on the PR. The loop runs on your OpenChamber server, so it keeps going with the app closed.

It ends when the PR is ready: CI is green, no review thread is left unresolved and nobody is waiting on requested changes. You get a notification then, and also when the loop stops for another reason.

## Start the loop

1. Open the session that should do the work.
2. Find the pull request in the [Issues and PRs](/issues-and-prs/) board, the pull request view, or the session's **Context sources** (the **⋮** menu on the PR's row), and choose **Start fix loop**.
3. Check the settings in the dialog and click **Start fix loop**.

The loop shows at the top of the session's message box: the PR, what the loop is doing, the iteration count and the CI state. From there you can change its settings, open the PR on the board, or **Stop** it.

## What the session receives

- **After a push**, the loop waits for CI on the new commit. If it fails, the session gets the failing checks once per commit, never the same failure twice.
- **For each review, review comment or new comment** that counts under your settings, the session gets its text and a link to it. The session is asked to reply on the PR and resolve the threads it fixed. To reply and resolve threads, the session needs its own authenticated GitHub tools. The loop's account is only used to read the PR.

If the session is busy, the message waits in its queue and goes out when the turn ends. If GitHub can't be reached, the loop keeps what it knew and says it couldn't check. It never reads a failed check as green.

Automatic mode accepts review feedback only from authors whose repository write access GitHub confirms. This also applies to older comments included as thread context. Allowed-author lists and mentions cannot bypass that check. If permission cannot be verified, the loop reports an error and waits. Approval mode can send external feedback to its restricted worker; publishing still needs your approval. Old queued automatic messages without verified admission stay blocked; remove them so the loop can read the feedback again.

## Settings

Defaults live in **Settings → Integrations → GitHub → Fix loop**, and each loop can change them.

- **Maximum iterations**: how many times the loop may send work to the session (default 10).
- **Token budget**: stop once the session has used this many tokens since the loop started. Empty means no budget. The budget is checked after each turn, so a turn can go past it.
- **Respond to**: **CI and reviews**, **CI only**, or **Reviews only**.
- **Ignore my feedback**: skip comments from the GitHub account the loop reads with. In automatic mode the session replies with its own GitHub account, and if that differs from the reading account, you add it to **Blocked authors**. In approval mode the server replies with the GitHub account bound to the loop, and the worker has no GitHub account.
- **Ignore bots**: skip comments from bots.
- **Allowed authors** and **Blocked authors**: GitHub logins, separated by commas. With an allow list, only those people count.
- **Only comments that mention this text**: count a comment only when it contains the mention text (`@openchamber` by default).
- **Push changes**: **Push automatically**, or **Wait for my approval**. Automatic mode keeps the session's own GitHub workflow. Approval mode runs the fixes in a restricted worker and needs its own setup.

## Approval mode

With **Wait for my approval**, the session doesn't push. A restricted worker fixes the PR in an isolated space, and no change is published to GitHub until you approve the exact commit. The server still reads the PR from GitHub while the loop runs.

### Set up the worker

1. Enable isolated spaces and configure a place for them. The fix loop never turns this on for you.
2. In the start dialog, find **Restricted worker**. Choose where the worker runs and its model, then click **Prepare new worker**. This creates a fresh space used only by this worker. An existing space can't be reused or converted.
3. Grant the worker's model access in the access dialog. Only the model you selected is granted. The gatekeeper holds the model tokens and the worker never sees them. The model use counts against your quota.
4. The PR's head repository, including a fork, needs a managed Git push destination for that exact repository. If it's missing, the dialog sends you to Git settings.
5. When the dialog says the worker is ready, click **Start fix loop**.

The worker can't reach GitHub or any other network, only the model. There is no fallback to a system or ambient Git push. The loop doesn't start if the worker isn't ready or access is missing. A model or custom endpoint that hasn't been reviewed for restricted workers is refused, never swapped for another one.

**Forget worker selection** removes only the selection. The space and its files stay, and you manage them in isolated spaces.

### Review and publish

When a turn finishes, the server exports the worker's commit and keeps it as a receipt with the exact repository, branch and expected remote head. The loop then shows **Review publication**. Open **Inspect exact changes**, check them, and click **Approve and publish commit**. The ordinary Git push button doesn't approve a receipt. Publication is refused if the PR closed or the remote head, branch or repository changed, and the receipt and the work stay for you to look at.

### Replies after publishing

The review dialog lists **Automatic GitHub replies**: the generated replies and which threads get resolved. They are the worker's text, so read the quoted text before approving. After the commit is published, the server posts the replies and resolves the threads with its own GitHub write access, which doesn't come from the worker. This happens with every client closed. If a write fails, the loop shows it and doesn't report the PR as ready.

### Stop, resume and budget

**Stop** stops the worker and keeps the code and the receipt. **Resume fix loop** checks the worker again and restarts it, and a receipt from a stopped loop can be published only after that. Forgetting a finished loop doesn't delete its space.

The execution mode is fixed for each loop. Complete any pending publication and GitHub replies before stopping the loop and starting another mode. Settings are also locked while a receipt or GitHub replies are pending.

The token budget is checked after each turn, so a turn can go past it. Once the budget is reached no new model turn starts, but a pending export, publication and replies can still finish. Then the loop shows the token budget status.

### Where approval mode works

The server runs the loop with every client closed. The web app, the desktop app and the mobile apps share it. The VS Code extension doesn't offer approval mode.

## When the loop stops

| Status | Why |
| --- | --- |
| PR is ready | CI green, no unresolved threads, no requested changes |
| PR closed | The PR was merged or closed |
| Iteration limit | The loop sent work as many times as allowed |
| Token budget | The session used up the budget |
| Stopped | You stopped it, or the session was deleted |

A loop that stopped stays at the top of the message box until you dismiss it. In approval mode with a pending receipt or GitHub replies, the work is retained and the loop stays; use **Resume fix loop** to continue the existing loop. Starting again on the same PR begins a new loop only when no publication or replies are pending.

## Stacks

Each pull request has its own loop. In a [stack](/stacked-prs/), start a loop on every PR you want fixed; a failure on one PR doesn't hold up the others.

## Where it works

The loop runs on the OpenChamber server behind the web app, the desktop app and the mobile apps. The VS Code extension doesn't offer it.
