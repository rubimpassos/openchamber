# PR 修正ループ

修正ループは、1 つのプルリクエストがマージ可能になるまでセッションに作業を続けさせます。OpenChamber は PR のチェックとレビューを監視します。CI が失敗すると、セッションは失敗したチェックを、そのステップ、アノテーション、ログ行とともに受け取ります。誰かがレビューやコメントをすると、セッションはそのフィードバックを受け取り、変更を行って PR に返信します。ループは OpenChamber サーバー上で動くため、アプリを閉じていても続きます。

PR の準備が整うと終了します。CI が通り、未解決のレビュースレッドがなく、変更依頼を待っている人もいない状態です。そのとき通知が届き、ほかの理由でループが止まったときにも届きます。

## ループを開始する

1. 作業を行わせるセッションを開きます。
2. [Issues と PR](/ja/issues-and-prs/) ボード、プルリクエストビュー、またはセッションの **Context sources**(PR の行の **⋮** メニュー)でプルリクエストを見つけ、**Start fix loop** を選びます。
3. ダイアログの設定を確認して **Start fix loop** をクリックします。

ループはセッションのメッセージ欄の上部に表示されます。PR、ループの動作内容、反復回数、CI の状態が確認できます。ここから設定の変更、ボードでの PR の表示、**Stop** での停止ができます。

## セッションが受け取るもの

- **push のあと**、ループは新しいコミットの CI を待ちます。失敗した場合、セッションは失敗したチェックをコミットごとに 1 回だけ受け取り、同じ失敗を 2 回受け取ることはありません。
- 設定上対象となる**レビュー、レビューコメント、新しいコメントごと**に、セッションはその本文とリンクを受け取ります。セッションは PR に返信し、修正したスレッドを解決するよう求められます。返信してスレッドを解決するには、セッションが認証済みの独自の GitHub ツールを持っている必要があります。ループのアカウントは PR の読み取りにだけ使われます。

セッションが処理中のときは、メッセージはキューで待ち、ターンが終わると送られます。GitHub に接続できない場合、ループはそれまでの状態を保持し、確認できなかったことを伝えます。失敗したチェックを成功と見なすことはありません。

## 設定

デフォルトは **Settings → Integrations → GitHub → Fix loop** にあり、ループごとに変更できます。

- **Maximum iterations**: ループがセッションに作業を送れる回数（デフォルトは 10）。
- **Token budget**: ループ開始後にセッションがこの数のトークンを使った時点で停止します。空欄は予算なしです。予算は各ターンの後に確認されるため、1 ターンで超過することがあります。
- **Respond to**: **CI and reviews**、**CI only**、**Reviews only**。
- **Ignore my feedback**: ループが PR の読み取りに使う GitHub アカウントのコメントをスキップします。自動モードではセッションが自分の GitHub アカウントで返信するので、読み取りアカウントと異なる場合は、そのアカウントを **Blocked authors** に追加してください。承認モードではサーバーがループに紐づく GitHub アカウントで返信し、ワーカーは GitHub アカウントを持ちません。
- **Ignore bots**: ボットのコメントをスキップします。
- **Allowed authors** と **Blocked authors**: カンマ区切りの GitHub ログイン名。許可リストがある場合、その人たちだけが対象になります。
- **Only comments that mention this text**: メンション用テキスト（デフォルトは `@openchamber`）を含むコメントだけを対象にします。
- **Push changes**: **Push automatically** または **Wait for my approval**。自動モードはセッション自身の GitHub ワークフローをそのまま使います。承認モードは修正を制限付きワーカーで実行し、専用のセットアップが必要です。

## 承認モード

**Wait for my approval** ではセッションは push しません。制限付きワーカーが隔離スペースで PR を修正し、あなたが正確なコミットを承認するまで、GitHub には変更が公開されません。ループの実行中も、サーバーは GitHub から PR を読み取り続けます。

### ワーカーをセットアップする

1. 隔離スペースを有効にし、その配置場所を設定します。修正ループがこれを勝手に有効にすることはありません。
2. 開始ダイアログで **Restricted worker** を探します。ワーカーを動かす場所とモデルを選び、**Prepare new worker** をクリックします。このワーカー専用の新しいスペースが作られます。既存のスペースは再利用も変換もできません。
3. アクセスダイアログで、ワーカーのモデルにアクセスを許可します。許可されるのは選んだモデルだけです。モデルのトークンはゲートキーパーが保持し、ワーカーには見えません。モデルの使用分はあなたのクォータから引かれます。
4. PR の head リポジトリは、フォークも含め、そのリポジトリ専用の管理された Git push 先が必要です。ない場合、ダイアログが Git 設定へ案内します。
5. ダイアログにワーカーの準備完了と表示されたら、**Start fix loop** をクリックします。

ワーカーが到達できるのはモデルだけで、GitHub にも他のネットワークにも届きません。システムや環境の push へのフォールバックはありません。ワーカーが準備できていない場合やアクセスがない場合、ループは始まりません。制限付きワーカー向けにレビューされていないモデルやカスタムエンドポイントは拒否され、別のものに切り替わることはありません。

**Forget worker selection** は選択を外すだけです。スペースとファイルは残り、隔離スペースで管理します。

### 確認して公開する

ターンが終わると、サーバーはワーカーのコミットをエクスポートし、正確なリポジトリ、ブランチ、想定するリモート head とともにレシートとして保持します。ループには **Review publication** が表示されます。**Inspect exact changes** を開いて内容を確認し、**Approve and publish commit** をクリックします。通常の Git push ボタンではレシートは承認されません。PR が閉じられた場合や、リモート head、ブランチ、リポジトリが変わった場合、公開は拒否され、レシートと作業内容は確認用に残ります。

### 公開後の返信

確認ダイアログの **Automatic GitHub replies** には、生成された返信と解決されるスレッドが並びます。これはワーカーが書いたテキストなので、承認する前に引用部分を読んでください。コミットが公開されると、サーバーは返信を投稿し、ワーカーとは別のサーバー自身の GitHub 書き込み権限でスレッドを解決します。すべてのクライアントを閉じていても動きます。書き込みが失敗するとループがそれを表示し、PR を ready とは報告しません。

### 停止、再開、予算

**Stop** はワーカーを止め、コードとレシートを残します。**Resume fix loop** はワーカーを再確認して起動し直します。停止したループのレシートを公開できるのは、その後です。完了したループを忘れても、そのスペースは削除されません。

実行モードはループごとに固定です。保留中の公開と GitHub 返信を完了してからループを停止し、別のモードを開始してください。レシートまたは GitHub 返信が保留中の間は、設定もロックされます。

トークン予算は各ターンの後に確認されるため、1 ターンで超えることがあります。予算に達すると新しいモデルターンは始まりませんが、保留中のエクスポート、公開、返信は完了できます。その後、ループはトークン予算の状態を表示します。

### 承認モードが使える場所

サーバーはすべてのクライアントを閉じていてもループを実行します。Web アプリ、デスクトップアプリ、モバイルアプリがこのサーバーを共有します。VS Code 拡張機能では承認モードを使えません。

## ループが止まるとき

| 状態 | 理由 |
| --- | --- |
| PR が準備完了 | CI が通り、未解決のスレッドも変更依頼もない |
| PR がクローズ | PR がマージまたはクローズされた |
| 反復回数の上限 | ループが許可された回数だけ作業を送った |
| トークン予算 | セッションが予算を使い切った |
| 停止 | ユーザーが停止した、またはセッションが削除された |

停止したループは、閉じるまでメッセージ欄の上部に残ります。承認モードでレシートまたは GitHub 返信が保留中の場合、作業は保持されてループも残るので、**Resume fix loop** で既存のループを続けます。同じ PR で新しいループを始められるのは、保留中の公開や返信がないときだけです。

## スタック

各プルリクエストには専用のループがあります。[スタック](/ja/stacked-prs/)では、修正したい PR ごとにループを開始してください。ある PR での失敗が、ほかの PR を止めることはありません。

## 対応環境

ループは、Web アプリ、デスクトップアプリ、モバイルアプリの背後にある OpenChamber サーバーで動きます。VS Code 拡張機能では利用できません。
